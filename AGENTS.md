# Инструкции для AI-агентов — Cosmic Samba

## Назначение и владелец

- Репозиторий: `krmobdev/cosmic-samba`.
- Проект: приложение для COSMIC Desktop для управления Samba и общими папками (Rust + libcosmic).
- Владелец проекта: Рустам.
- Общение с владельцем — на русском языке. Коммиты, названия веток и PR могут быть на английском, если так понятнее.
- Этот файл — основной источник правил работы агента. При начале каждой задачи прочитать его и проверить актуальную ветку, состояние Git и CI.

## Ветки и Git workflow

- `main` — стабильная ветка. Содержит только проверенное состояние проекта.
- `dev` — основная рабочая и интеграционная ветка. **Вся текущая разработка ведётся в `dev`.**
- Перед началом работы проверить, что целевая ветка — `dev`, и получить её актуальное состояние.
- По умолчанию вносить изменения непосредственно в `dev`. Не создавать дополнительные рабочие ветки без реальной необходимости или просьбы владельца.
- Если для изоляции задачи всё же нужна отдельная ветка, создавать её от актуального `dev`; PR направлять обратно в `dev`, никогда не в `main`.
- Не отправлять рабочие коммиты и PR в `main`. Не менять default branch.
- **Не выполнять merge в `main`, push в `main`, cherry-pick в `main` или иные изменения `main` без отдельного прямого разрешения владельца.** Просьбы «работай», «исправь», «доведи», «подготовь» не являются разрешением на слияние.
- Перенос проверенного состояния из `dev` в `main` делать только по прямой просьбе владельца. Перед этим показать/проверить diff, результаты CI и тестов.
- Не удалять ветки и не переписывать историю (force-push, reset опубликованных веток) без прямого разрешения.
- Не закрывать и не сливать PR автоматически только потому, что CI зелёный.
- После каждого изменения сообщать владельцу, в какой ветке оно сделано, что изменено, SHA коммита и состояние проверок. Не заявлять о выполнении действий, которые фактически не были выполнены.

## Правила разработки

- Сначала изучить существующую архитектуру, README, Cargo.toml, CI и затрагиваемые исходники. Не угадывать API COSMIC/libcosmic — сверяться с текущими зависимостями и документацией.
- Делать минимальные целевые изменения. Не переписывать соседний код и не менять несвязанные файлы без необходимости.
- Не добавлять новые зависимости без обоснования.
- Не ослаблять проверки, обработку ошибок, валидацию или безопасность ради прохождения тестов.
- Привилегированные операции Samba и системные изменения выполнять только через предусмотренный безопасный helper. Не запускать команды через shell с конкатенацией пользовательского ввода; аргументы передавать раздельно.
- Не раскрывать пароли, токены, ключи и другие секреты. Не добавлять секреты, локальные конфиги, приватные ключи или временные файлы в Git.
- Не считать успешную компиляцию доказательством корректной работы приложения или реальной интеграции с Samba/COSMIC.
- Не менять UX, структуру интерфейса или публичное поведение без связи с задачей либо согласования с владельцем.

## Проверки и готовность

- Для изменений Rust запускать доступные проверки проекта: `cargo fmt --all -- --check`, `cargo check`, `cargo test` и `cargo clippy --all-targets --all-features -- -D warnings` (если параметры совместимы с текущим проектом).
- Проверять release-сборку, когда изменения затрагивают сборку/упаковку или когда это необходимо для готовности к запуску.
- Проверять GitHub Actions для актуального коммита/PR. Не считать queued или in_progress успешным результатом.
- При падении проверки выяснить причину и исправить её в `dev`; не маскировать ошибку и не менять workflow так, чтобы он перестал проверять качество.
- Отдельно проверять установку и запуск в реальной COSMIC-сессии, системные разрешения/pkexec и операции с реальным Samba. Если такой проверки не было, прямо указывать это как непроверенную часть.
- Не обещать, что приложение готово к использованию, только на основании CI.

## Установка и выпуск

- `main` — стабильная линия; `dev` — рабочая линия.
- Не публиковать релизы, пакеты, Flatpak, DEB или другие артефакты как стабильный выпуск без прямого запроса владельца.
- Не менять версии, release metadata, подписи или настройки публикации без необходимости и явного согласования.
- Сначала доводить изменения и проверки в `dev`. Подготовка к выпуску не означает разрешение на перенос в `main`.

## Коммуникация и отчёт

- Отвечать по-русски, коротко и конкретно.
- Сначала сообщать фактический результат, затем оставшиеся проблемы и непроверенные сценарии.
- Разделять подтверждённое CI, локальные проверки и ручную проверку на целевой системе.
- Если действие невозможно выполнить доступными инструментами, честно сказать об этом и не имитировать результат.
